# 审计报告：怎么读底稿，怎么写结论

`audit_run.py` 给出事实。审计报告是你对这些事实的判断：哪里花得不值、根因是什么、改什么、怎么验证。读者通常是负责部署和调优的人，他要的是“接下来改哪三个设置”，不是指标大全。

## 读数陷阱

这些都是真的踩过的：

- **模型秒、工具秒是各调用之和**。步骤并行执行，所以它们会远大于活跃时长。判断瓶颈看比例和“轮间秒”，不要把它们相加当总时长。
- **等待时长**是用户确认计划、网关停机的时间，不是性能问题。
- **两次运行不可直接比总量**。规划器每次给出的步骤数、搜索次数不同。先比比例（命中率、每条引用 Token、每次调用 P50、错误率），再看总量。
- **缓存命中要分两层看**。“可复用前缀”是同一会话里与上一次请求从头相同的提示词占比，即命中率的上限，由我们的请求构造决定；“缓存命中”是供应商上报的。前者低 → 请求开头被改写（看前缀断点表）；前者高后者低 → 模型服务没开 prefix caching、网关多副本没有会话粘性，或两轮间隔超过缓存有效期。
- **有些请求天然命中不了**：每个会话的第一轮、大纲（单次调用）、每份报告第一次被追问、压缩发生后的那一轮、同时起跑的并行请求之间。单轮节点命中率低不是缺陷。
- **供应商逐轮核对为 0/N** 只说明供应商没上报缓存 Token（很多网关不上报），不代表没命中；这时看单次调用耗时有没有随上下文增长而线性变慢。
- **`run.usage` 不是这次研究的总用量**：预算按任务计，报告完成后的每次追问都会把它清零并把上一段存进 `usage_history`。总量看底稿第 3 节（来自逐次调用记录）。
- **失败的运行和成功的运行对比总量没有意义**（失败的几乎全是 0）。要比就比每个步骤的 Token 与轮数（底稿的 Agent 循环表），用来回答“正常情况下一步要花多少”。
- **`null` / “—” 是没有测量**（早于该指标的记录、网关不上报用量），不是 0。不要拿它算平均。
- **`unreported` 用量**：成功的调用没上报 Token 才是问题（`stream_usage`）；失败或被中断的调用本来就没有用量。
- **重试/修复要数调用，不要数事件**。产品的“格式重试”数的是事件，修复后仍不合格会再记一条但不再调用模型；底稿的“重做的模型调用”才是成本（同一任务的第二次及以后的调用）。看比例：13 次章节调用里 5 次是重做，写作成本多了六成；1 次不值得动设置。
- **`prompts_differing_from_current_defaults` 不等于“用户改过提示词”**：它是和**当前代码**的默认值比的，默认值后来改过，旧运行就会显示为不同。
- **补研步骤的耗时**要和它带来的证据一起看：补研后缺口没变、引用没增加，就是白花的。底稿“研究轮次的成本与产出”按**第一次读到证据的轮次**归属；补研步骤会继承父步骤的证据，所以首轮读到、补研又用到的仍算首轮，不要把补研步骤的“原始证据”数当成它的产出。“被引用的发现”为“—”说明证据合并无法重放（旧契约的记录），不是 0。
- **“白等秒”和“推算（无失败调用）”是估计**：把失败的调用换成该工具成功调用的中位耗时，再按同样的并发重排。它回答“供应商正常的话大概多久”，不是承诺；供应商修好后实际的成功耗时可能更长或更短。写进报告时标明是推算。
- **指标全绿不等于交付了**。脚本看不到报告内容是否回答了请求。对照请求检查报告（用户要“每一代的对比”，表里有没有每一代），缺口的根因通常写在对应步骤最后一轮的研究笔记里。
- **证据“裁剪”很大**通常是搜索结果里的链接（只证明“发现过”），不是丢了被引用的证据。

## 取证标准

- 每个结论至少有一个数字和它的出处（底稿第几节的哪张表，或 `call_id`）。
- 涉及“模型为什么这么做”的判断，打开那次调用看原文（`show_call.py`），不要从指标反推。
- 区分**事实**（记录里有）、**推断**（由事实推出，说明推理）、**建议**（要改什么）。没验证的推断不要写成事实。
- 引用调用内容时只摘必要的片段；不要贴凭据、Cookie、整段内部文档。

## 报告模板

默认中文；文件名 `审计报告-<run8>.md`，和底稿放在一起。篇幅以一屏半到三屏为宜，细表留在底稿里，用“见底稿第 N 节”引用。

```markdown
# DeepResearch 审计报告：<run8>

- 研究请求：<一句话>
- 结果：<COMPLETED/FAILED + 错误码>；<总时长>；<输入/输出 Token，命中率>；<引用数、字符数>
- 运行环境：<模型、并发、关键设置：补研缺口、预算、报告长度>
- 数据来源：<research.sqlite3 路径或网关>；底稿 `audit-<run8>.md`，页面 `audit-<run8>.html`

## 结论（三到五条，按影响排序）
1. <最重要的一条：现象 + 根因 + 量级>。例：11 分钟里 9 分钟在等搜索供应商：serper 鉴权失败 51 次、tavily 配额用尽 63 次，每次搜索要失败两轮才轮到 duckduckgo。
2. …

## 交付物
<对照请求：用户要的每一项有没有交付、覆盖全不全；没交付的部分，根因在哪一步（引用那一步最后一轮笔记的原文）>

## 时间
<模型/工具/排队/等待各占多少；关键路径是哪一步、哪个节点；失败的工具调用让各步骤白等了多少、去掉后每轮大约多久（推算）；最慢的调用说明了什么>

## Token 与缓存
<哪个节点占大头；Agent 循环的上下文增长；可复用前缀 vs 缓存命中及其含义；是否有截断、压缩>

## 检索与工具
<错误率与错误类型；供应商表现；重复调用；搜索预算；失败站点>

## 研究与报告质量信号
<计划步骤与补研（触发原因；补研轮的时间与 Token 占比对比它带来的被引用来源占比）；被提前收尾的步骤；无发现的步骤；章节修复与删除陈述；引用与来源分布；结束时仍在的缺口>

## 根因取证
<对结论里最重要的两三条，给出打开的 call_id、看到了什么（摘几十个字）、由此确定或排除了什么>

## 调优建议
| 优先级 | 改什么（具体设置与取值） | 依据 | 预期变化 | 风险 |
| --- | --- | --- | --- | --- |

## 验证
<已做：与基线对比的结果（先比例后总量）。未做：建议的验证方法——同一问题、只改一类设置、用 --baseline 对比哪几项>

## 未能确定的事
<数据缺失（未上报用量、早于审计的记录）、需要目标环境才能验证的推断>
```

## 写作要求

- 第一段就给判断，不要用“本报告将……”开场。
- 数字带单位和分母（“8/13 次章节调用触发了修复”，而不是“修复较多”）。
- 建议必须可执行：写出设置名和取值（`supplement_gap_codes: [coverage, unsupported]`），设置含义查 `docs/deepresearch/RESEARCH_CONFIGURATION.md`，症状到设置的对应见 [tuning.md](tuning.md)。
- 运行失败时，报告以根因和恢复路径为主（能否从检查点重试、要先改什么），性能部分从简。
- 运行还在进行（`in_progress`）时说明这是中途快照。
